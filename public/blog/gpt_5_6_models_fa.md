<h2 id="models">تفاوت Sol، Terra و Luna</h2>

| مدل | مناسب برای | قیمت استاندارد API به‌ازای ۱ میلیون توکن |
| --- | --- | --- |
| `gpt-5.6-sol` | تحلیل دشوار، کدنویسی حساس و بازبینی عمیق | ورودی ۵ دلار / خروجی ۳۰ دلار |
| `gpt-5.6-terra` | گفت‌وگو، اتوماسیون سازمانی و بیشتر کارهای محصول | ورودی ۲٫۵ دلار / خروجی ۱۵ دلار |
| `gpt-5.6-luna` | دسته‌بندی، استخراج و پردازش حجم زیادی از داده | ورودی ۱ دلار / خروجی ۶ دلار |

هر سه مدل پنجره زمینه ۱٬۰۵۰٬۰۰۰ توکنی، حداکثر ورودی ۹۲۲٬۰۰۰ توکن و حداکثر خروجی ۱۲۸٬۰۰۰ توکن دارند. البته این ظرفیت بالا به این معنی نیست که همیشه باید متن‌های بسیار طولانی بفرستید. زمینه اضافی می‌تواند هزینه و زمان پاسخ را بالا ببرد و حتی مدل را از موضوع اصلی دور کند.

<h2 id="pricing">قیمت و دسترسی</h2>

قیمت‌های جدول مربوط به حالت استاندارد API هستند. هزینه Batch، Flex، Priority، ابزارهای میزبانی‌شده یا پردازش منطقه‌ای ممکن است متفاوت باشد. ورودی ذخیره‌شده در cache ارزان‌تر است، اما هزینه نهایی فقط به تعداد توکن بستگی ندارد؛ تعداد رفت‌وبرگشت‌ها، ابزارهای استفاده‌شده، طول پاسخ و تلاش استدلالی هم روی آن اثر می‌گذارند.

طبق معرفی OpenAI، این خانواده در ChatGPT، Codex و OpenAI API عرضه شده است. البته دسترسی به مدل‌ها و حالت‌های مختلف می‌تواند به نوع اشتراک و روند انتشار وابسته باشد. برای ساخت گردش‌کارهای چندمرحله‌ای و استفاده از ابزارها در API، معمولا Responses API انتخاب مناسب‌تری است.

<h2 id="coding">برنامه‌نویسی و عامل‌های نرم‌افزاری</h2>

برای سنجش یک مدل برنامه‌نویسی، یک prompt بزرگ به‌تنهایی کافی نیست. بهتر است کاری واقعی به آن بدهید؛ مثلا ساختار پروژه را بررسی کند، چند فایل را تغییر دهد، تست‌ها را اجرا کند و محدودیت‌ها را توضیح دهد. بعد می‌توانید کیفیت کد، کامل بودن تست‌ها، زمان اجرا، مصرف توکن و میزان دخالت انسانی را مقایسه کنید.

OpenAI برای Sol نتایجی مثل ۸۸٫۸ درصد در Terminal-Bench 2.1، امتیاز ۶۴٫۶ درصد در SWE-Bench Pro و ۷۲٫۷ درصد در DeepSWE v1.1 گزارش کرده است. این اعداد امیدوارکننده‌اند، اما عملکرد مدل در پروژه شما را تضمین نمی‌کنند. بهترین معیار، مجموعه کوچکی از باگ‌ها و تغییرات واقعی تیم خودتان است.

<h2 id="reasoning">Multi-agent و حالت‌های استدلال</h2>

قابلیت آزمایشی **Multi-agent** در Responses API به یک عامل اصلی اجازه می‌دهد چند عامل فرعی را هم‌زمان مدیریت کند. این روش زمانی مفید است که کار واقعا قابل تقسیم باشد؛ مثلا یک عامل مخزن را بخواند، یکی تست‌ها را بررسی کند و دیگری مستندات را ببیند. برای کارهای ساده یا مرحله‌هایی که کاملا به هم وابسته‌اند، استفاده از چند عامل معمولا فقط هزینه و پیچیدگی را بیشتر می‌کند.

گزینه `reasoning.effort` مقدار تلاش استدلالی مدل را تعیین می‌کند. `medium` نقطه شروع خوبی است و بهتر است `high`، `xhigh` یا `max` را فقط زمانی انتخاب کنید که در آزمایش‌های خودتان تفاوت محسوسی دیده باشید. **Pro mode** هم مدل جداگانه‌ای نیست و با `reasoning.mode: "pro"` فعال می‌شود. این حالت برای اطمینان بیشتر، زمان و توکن بیشتری مصرف می‌کند.

حالت `ultra` در ChatGPT و Codex نیز می‌تواند چند عامل را هم‌زمان هماهنگ کند، اما با قابلیت Multi-agent در API یکی نیست؛ یکی حالت محصول است و دیگری تنظیمات جداگانه‌ای در API دارد.

<h2 id="ptc">Programmatic Tool Calling چیست؟</h2>

در فراخوانی معمولی ابزار، مدل بعد از هر نتیجه دوباره تصمیم می‌گیرد. **Programmatic Tool Calling یا PTC** به مدل اجازه می‌دهد یک قطعه JavaScript کوچک را در محیطی جدا اجرا کند، چند ابزار مجاز را صدا بزند، نتیجه‌ها را فیلتر یا ترکیب کند و فقط اطلاعات لازم را برگرداند. این روش برای داده‌های میانی بزرگ، حلقه‌ها، مرتب‌سازی و فراخوانی‌های موازی مفید است.

PTC برای همه کارها مناسب نیست. اگر نتیجه هر ابزار مسیر مرحله بعد را تغییر می‌دهد، کار به تأیید انسان نیاز دارد یا باید خروجی اصلی ابزارها حفظ شود، فراخوانی مستقیم شفاف‌تر است. محیط PTC نیز به Node.js، فایل‌سیستم، شبکه مستقیم یا نصب package دسترسی ندارد و فقط می‌تواند از ابزارهای مجاز استفاده کند.

<h2 id="documents">سند، ارائه و رابط کاربری</h2>

OpenAI از بهتر شدن مدل در طراحی، چیدمان بصری و پیروی از قالب مرجع گفته است. این ویژگی‌ها برای ساخت پیش‌نویس سند، ارائه، spreadsheet یا رابط فرانت‌اند مفیدند؛ به‌خصوص وقتی فایل نمونه، design system و معیار پذیرش مشخصی در اختیار مدل باشد.

ظاهر خوب همیشه به معنی نتیجه درست نیست. عددها، فرمول‌ها، نام‌ها، تاریخ‌ها و دسترس‌پذیری را جداگانه بررسی کنید. در پروژه وب هم صفحه را در اندازه‌های مختلف ببینید، کار با کیبورد را آزمایش کنید و تست‌ها را اجرا کنید.

<h2 id="safety-domains">علم، سلامت و امنیت سایبری</h2>

طبق گزارش رسمی، این مدل‌ها در علم، سلامت و دفاع سایبری بهتر شده‌اند، اما همچنان نباید جای متخصص، بررسی بالینی یا فرایند امنیتی سازمان را بگیرند. نتیجه‌های حساس باید با منبع اصلی و نظر متخصص بررسی شوند.

System Card توانایی‌های سایبری و زیستی یا شیمیایی هر سه مدل را در سطح «High» قرار داده، نه «Critical». استفاده مناسب در محیط کاری بیشتر شامل کارهای دفاعی مثل code review، threat modeling، رفع آسیب‌پذیری و بررسی patch است، نه اجرای خودکار عملیات روی سامانه‌های دیگران.

<h2 id="limits">محدودیت‌ها و کنترل انسانی</h2>

عامل‌های طولانی‌مدت ممکن است از خواسته کاربر فراتر بروند، بیش از حد مطمئن حرف بزنند یا ابزار نامناسبی انتخاب کنند. به همین دلیل بهتر است دسترسی ابزارها محدود باشد، عملیات حساس بدون تأیید انسان انجام نشود و برای کارهای چندمرحله‌ای، گزارش اجرا و شرط توقف مشخص داشته باشید. ادعاهای واقعی را با منبع و خروجی‌های محاسباتی را با تست مستقل بررسی کنید.

OpenAI از پایش هم‌زمان و کنترل‌های دسترسی برای حوزه‌های حساس استفاده می‌کند، اما طراحی درست گردش‌کار، تعیین مجوز ابزارها و بازبینی خروجی همچنان بر عهده سازنده محصول است.

<h2 id="selection">کدام مدل برای چه کاری مناسب است؟</h2>

برای کارهای پرتعداد و کم‌ریسک مثل استخراج اطلاعات، برچسب‌گذاری و خلاصه‌سازی کنترل‌شده، از **Luna** شروع کنید. **Terra** برای گفت‌وگوهای محصول و اتوماسیون‌های معمول انتخاب متعادلی است. **Sol** را برای مسئله‌های دشوار، مبهم یا پرریسکی نگه دارید که کیفیت بیشتر، هزینه و زمان بالاتر را توجیه می‌کند. اگر اعتماد مدل پایین بود، تست شکست خورد یا خروجی اثر بیرونی داشت، آن را به مدل قوی‌تر یا بازبینی انسان بسپارید.

در نهایت، انتخاب مدل یک تصمیم ثابت نیست. آن را روی نمونه‌های واقعی آزمایش کنید و هر زمان مدل یا قیمت‌ها تغییر کردند، دوباره ارزیابی را انجام دهید.
